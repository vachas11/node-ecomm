📋 Example Flow 1: User Registration

Scenario: New user creates an account

Step 1: Client → API Gateway
POST /api/auth/register
Body: { email: "user@example.com", password: "SecurePass123", firstName: "John", lastName: "Doe" }
Step 2: API Gateway
✓ Check rate limit (Redis: INCR ratelimit:192.168.1.1)
✓ Validate request body
✓ Route to User Service
Step 3: User Service → PostgreSQL
✓ Check if email already exists: SELECT * FROM users WHERE email = ?
✓ If exists → Return 409 Conflict
✓ Hash password using bcrypt.hash(password, 10) from utils/password.ts
✓ Create user: INSERT INTO users (email, password_hash, first_name, last_name)
✓ Store in PostgreSQL (User DB)
Step 4: User Service → Message Queue
✓ Publish event: user.registered
Payload: { userId: 123, email: "user@example.com", firstName: "John", registeredAt: "2024-01-15T10:30:00Z" }
Step 5: User Service → API Gateway
✓ Generate JWT tokens using shared/auth/jwt.ts:
  - Access Token (15 min expiry)
  - Refresh Token (7 days expiry)
✓ Store refresh token in PostgreSQL: INSERT INTO refresh_tokens
Response: 201 Created with { accessToken, refreshToken, user: { id, email, firstName } }
Step 6: API Gateway → Client
✓ Record metrics (Prometheus): user_registration_total++
✓ Return response to client
Step 7 (Async): Message Queue → Notification Service
✓ Notification Service subscribes to user.registered event
✓ Receive event from queue
✓ Generate welcome email from template
✓ Send email: "Welcome to E-Commerce Platform!"
✓ Log notification sent

Key Points:

  • Synchronous: Client → Gateway → User Service (immediate response)
  • Asynchronous: User Service → Queue → Notification Service (fire-and-forget)
  • Shared Library: Uses shared/auth/jwt.ts for token generation
  • Cache: Rate limiting uses Redis
  • Database: User stored in PostgreSQL

📦 Example Flow 2: Place Order (with Inventory Update & Notification)

Scenario: User places an order for products

Step 1: Client → API Gateway
POST /api/orders
Headers: Authorization: Bearer <jwt_token>
Body: { products: [{ productId: 101, quantity: 2 }, { productId: 202, quantity: 1 }], shippingAddress: {...} }
Step 2: API Gateway
✓ Verify JWT token using shared/auth/jwt.ts → verifyToken()
✓ Check token not in blacklist (Redis: GET blacklist:<token>)
✓ Check rate limit (Redis: INCR ratelimit:user:123)
✓ Extract userId from token: userId = 123
✓ Route to Order Service
Step 3: Order Service → User Service (Internal API)
GET /internal/users/123/validate
User Service checks: User exists? Active? Has valid profile?
Response: { id: 123, email: "user@example.com", isActive: true }
Step 4: Order Service → Product Service (Internal API)
POST /internal/products/check-inventory
Body: [{ productId: 101, quantity: 2 }, { productId: 202, quantity: 1 }]
Product Service checks stock availability
Response: { available: true, items: [{ productId: 101, inStock: 50, price: 29.99 }, ...] }
Step 5: Order Service
✓ Calculate total amount: total = (2 × $29.99) + (1 × $49.99) = $109.97
✓ Create order record in PostgreSQL (Order DB):
  INSERT INTO orders (user_id, total_amount, status) VALUES (123, 109.97, 'pending')
  INSERT INTO order_items (order_id, product_id, quantity, price)
✓ Cache order in Redis: SET order:456 {...} with 1 hour TTL
Step 6: Order Service → Payment Service (Internal API)
POST /internal/payments/process
Body: { orderId: 456, amount: 109.97, userId: 123 }
Payment Service processes payment with external gateway
Store transaction in PostgreSQL (Payment DB)
Response: { transactionId: "txn_789", status: "success" }
Step 7: Order Service → PostgreSQL
✓ Update order status: UPDATE orders SET status = 'paid', transaction_id = 'txn_789' WHERE id = 456
Step 8: Order Service → Message Queue
✓ Publish event: order.created
Payload: { orderId: 456, userId: 123, items: [{productId: 101, quantity: 2}, ...], totalAmount: 109.97 }
Step 9: Payment Service → Message Queue
✓ Publish event: payment.completed
Payload: { orderId: 456, transactionId: "txn_789", amount: 109.97, status: "success" }
Step 10: Order Service → API Gateway → Client
✓ Return response: 201 Created
Body: { orderId: 456, status: "paid", totalAmount: 109.97, estimatedDelivery: "2024-01-20" }
Step 11 (Async): Message Queue → Product Service
✓ Product Service subscribes to order.created event
✓ Receive event, extract product IDs and quantities
✓ Deduct inventory in PostgreSQL (Product DB):
  UPDATE inventory SET quantity = quantity - 2 WHERE product_id = 101
  UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 202
✓ Check if inventory low → Publish inventory.updated event
Step 12 (Async): Message Queue → Notification Service
✓ Notification Service subscribes to order.created AND payment.completed events
✓ Receive both events
✓ Generate order confirmation email
✓ Send email: "Order #456 Confirmed - Total: $109.97"
✓ Send SMS: "Your order has been placed successfully!"

Key Points:

  • Synchronous Chain: Order → User (validate) → Product (check inventory) → Payment (process)
  • Asynchronous Events: Order Service & Payment Service publish to queue
  • Event Consumers: Product Service (inventory update), Notification Service (email/SMS)
  • Shared Library: API Gateway uses shared/auth/jwt.ts and shared/auth/middleware.ts
  • Cache Usage: Order cached in Redis for quick retrieval
  • Database per Service: Order DB, Product DB, Payment DB are separate

🚪 Example Flow 3: User Logout (Token Blacklist)

Scenario: User logs out, token must be invalidated

Step 1: Client → API Gateway
POST /api/auth/logout
Headers: Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Step 2: API Gateway
✓ Verify JWT token using shared/auth/jwt.ts → verifyToken()
✓ Extract userId and token expiry: { userId: 123, exp: 1705320000 }
✓ Route to User Service (logout endpoint)
Step 3: User Service → Redis (Blacklist Token)
✓ Add token to blacklist using shared/auth/blacklist.ts → addToBlacklist()
✓ Redis command: SET blacklist:eyJhbGciOi... "revoked" EX 900
  (EX 900 = expires in 15 minutes, matching token's remaining lifetime)
✓ This ensures token cannot be reused until it naturally expires
Step 4: User Service → PostgreSQL (Delete Refresh Token)
✓ Find refresh token associated with this user:
  SELECT * FROM refresh_tokens WHERE user_id = 123
✓ Delete refresh token from database:
  DELETE FROM refresh_tokens WHERE user_id = 123 AND token = 'refresh_token_hash'
✓ User cannot get new access token without logging in again
Step 5: User Service → Redis (Clear Session Cache)
✓ Delete user session from cache:
  DEL session:user:123
✓ Clear any other user-specific cached data
Step 6: User Service → API Gateway → Client
✓ Return response: 200 OK
Body: { message: "Logged out successfully" }
Step 7: Client
✓ Client deletes tokens from local storage
✓ Redirects to login page
Step 8 (Future Request): Token Reuse Prevention
✓ If client tries to use old token: Authorization: Bearer eyJhbGciOi...
✓ API Gateway checks blacklist (Redis: GET blacklist:eyJhbGciOi...)
✓ Finds token in blacklist → Returns 401 Unauthorized
✓ Client must login again to get new tokens

Key Points:

  • Shared Library: Uses shared/auth/blacklist.ts for token blacklisting logic
  • Redis Blacklist: Fast in-memory check prevents token reuse
  • TTL Optimization: Blacklist entry expires when token would naturally expire (no storage waste)
  • Database Cleanup: Refresh token deleted from PostgreSQL
  • Session Cache: User session removed from Redis
  • Security: Multi-layer invalidation ensures token cannot be reused

🔗 Shared Library Details (shared/auth/)

Purpose: Consistent authentication behavior across all services

1. jwt.ts - JWT Token Management

  • generateAccessToken(userId, email, role) → Creates JWT with 15-min expiry
  • generateRefreshToken(userId) → Creates refresh token with 7-day expiry
  • verifyToken(token) → Validates JWT signature and expiry
  • Used by: API Gateway (verify incoming requests), User Service (generate on login)

2. middleware.ts - Authentication Middleware

  • authenticateToken(req, res, next) → Express middleware for protected routes
  • Extracts JWT from Authorization header
  • Verifies token using jwt.ts
  • Checks blacklist using blacklist.ts
  • Attaches req.user = { userId, email, role } to request
  • Used by: All services for protected endpoints

3. blacklist.ts - Token Blacklist Management

  • addToBlacklist(token, expirySeconds) → Add token to Redis with TTL
  • isBlacklisted(token) → Check if token is revoked
  • removeFromBlacklist(token) → Remove token (rarely used)
  • Used by: API Gateway (check on every request), User Service (add on logout)

4. rateLimiter.ts - Rate Limiting Logic

  • checkRateLimit(key, maxRequests, windowSeconds) → Returns { allowed: boolean, remaining: number }
  • Uses Redis INCR with TTL: INCR ratelimit:{key}
  • Example: Max 100 requests per minute per IP
  • Used by: API Gateway (on every incoming request)

🎯 Summary: Communication Patterns

Synchronous Communication (REST APIs)

  • Client ↔ API Gateway (all external requests)
  • API Gateway → Microservices (routing)
  • Order Service → User Service (validate user)
  • Order Service → Product Service (check inventory)
  • Order Service → Payment Service (process payment)
  • When to use: Need immediate response, transactional operations

Asynchronous Communication (Message Queue)

  • User Service → Queue → Notification Service (welcome email)
  • Order Service → Queue → Product Service (inventory update)
  • Order Service → Queue → Notification Service (order confirmation)
  • Payment Service → Queue → Notification Service (payment receipt)
  • When to use: Fire-and-forget operations, decoupled services, background tasks

Shared Data Access

  • Redis: All services read/write to shared cache (blacklist, rate limits, sessions)
  • Shared Library: All services import shared/auth/ for consistent auth behavior
  • Monitoring: All services expose /metrics scraped by Prometheus
